# SoCcentric STM32

The website of SoCcentric STM32 (https://soccentric-stm32.github.io/). Open-source building blocks for STM32 projects: an A/B bootloader and its flasher GUI, C and Rust applications on FreeRTOS, Zephyr and Embassy, hardware validation firmware and GUI, a factory provisioning station, the factory firmware and a factory data GUI. All MIT licensed. Consulting contact details are on the Contact section only.

## Features

- One-page site with full-height slides and scroll snapping
- Hero showcase with a capture of all twelve building blocks: pick one from
  the reel, or use the arrow keys
- One slide per project with what is in the repository (build environment,
  architecture, design, implementation, tests and app features)
- Screen captures of the four desktop tools and, on every firmware slide, a
  terminal that replays the real debug log recorded from the board
- Light and dark theme
- Header menu with dropdowns and deep links to each project
- No framework: HTML, CSS and one small script; `make check` validates links,
  captures and metadata
- Self-hosted fonts, no third-party requests and no cookies
- Works without JavaScript
- Social preview image, sitemap and structured metadata
- Branded 404 page

## Build and run

```bash
make check                    # validate links, captures and page metadata
make serve                    # then open http://localhost:8000/
```

`make check` is the repository's build target; it needs only Python 3. Pushing
to `main` deploys the site with GitHub Pages.

## Screen captures

The pictures in `assets/shots/` are real captures, not mock-ups:

- `bootloader-gui` is BOOT Flasher after a real Build, Sign & Flash of the C
  FreeRTOS app onto the NUCLEO-F767ZI: the four steps, the `bootctl` output and
  the debug UART read live from USART6. The application ran under Xvfb with the
  serial ports visible and was driven only through its own button.
- `factory-station` is HWVAL Factory's Detect page on the same bench: the
  ST-LINK probe and the UART ports it found. Detecting only lists devices.
- `validation-gui` still comes from the application's built-in simulator, which
  is why it shows 196 tests; the real firmware reports 201.
- `factory-data-gui` is regenerated by `make shots` (`ci/capture_screens.py`),
  which runs the Factory Data GUI under Xvfb. It needs Pillow, a Chromium
  binary, Xvfb, PySide6 and the sibling `factory-data-gui` checkout.

## Recorded logs

The terminals are recorded logs, not pictures. `assets/logs/<slide>.log` holds
the debug log (USART6, 115200 8N1) exactly as the NUCLEO-F767ZI sent it, from a
reset: BOOT's own start-up lines (clock, USART3, scan for an application, flash,
both slots, selection, the 500 ms listen window, hand-over), then the
application's trial boot, its four task lines every second and the health check
that confirms it. The bootloader slide starts from `openocd ... reset run`; the
others from `make flash`, whose last line is `Activate: ok, device is resetting`.

`index.html` carries the same lines, each with a replay time (`data-t`), and
`assets/main.js` plays them line by line while the slide is on screen, with the
newest line in view and a cursor behind it. BOOT's start-up is replayed three
times slower so it can be read; the rest runs at the recorded pace. The hero
showcase plays the same logs. With JavaScript off, or with reduced motion, the
whole log is simply shown.

- `assets/video/bootloader/` keeps the board recordings: for BOOT and each of
  the six apps a `<name>.webm` (BOOT Flasher), `term-<name>.webm` (the UART log
  read live from USART6), `<name>.log` (the same log as text) and two `.webp`
  posters. `python3 ci/record_session.py all` makes them. It **flashes the
  connected board** (BOOT over SWD, then each app through BOOT), so it is not
  part of `make`. It needs Xvfb, ffmpeg with libvpx-vp9, openocd, PySide6,
  pyserial, a NUCLEO-F767ZI on its ST-LINK port and a USB serial adapter on
  PG14. The current page does not link these recordings.

The terminals are live HTML, so text stays crisp and theme-aware.
