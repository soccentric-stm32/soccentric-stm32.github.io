Open STM32 building blocks

A complete STM32 product, from boot to factory floor.

Eight open-source projects that work together: an A/B bootloader, the same application in C/C++ and in Rust on both FreeRTOS and Zephyr, validation firmware with a desktop GUI, and a factory test and provisioning station. The bootloader, the application builds, the validation firmware and the bench app share one boot contract and one host protocol (HWLINK); the factory station is the production-line counterpart. I'm Sandesh Ghimire, and I use them as the baseline for every STM32 project I build.

01Bootloader

A/B bootloader, updates that can't brick

A bare-metal bootloader with two application slots, one in each flash bank. A new image is written to the inactive slot, verified, trial-booted and kept only when the application confirms it is healthy. Otherwise the bootloader rolls back to the last good image.

Bare metal · CFeature-complete · v0.1

Features

  • Dual-bank A/B slots; the same binary runs from either slot through a bank swap
  • Firmware update over UART (HWLINK) at 115200 or 921600 baud
  • 256-byte image header; CRC32 of the header and of the slot read back from flash
  • Trial boot with a boot counter, 4 s IWDG and automatic rollback after three failed starts
  • Append-only metadata records with CRC, safe against power loss
  • Host tools: mkimage.py to build images, bootctl.py to inspect, update and activate
  • About 28 KB of flash; no RTOS, no dynamic memory

02RTOS · FreeRTOS

FreeRTOS application in C/C++

The reference application and the template for new products. It runs under the A/B bootloader, talks to the host over HWLINK, supervises its own tasks and confirms a new image only after a health check.

C · FreeRTOS · STM32CubeF7Feature-complete

Features

  • Four tasks: Health, Comms, Button and LED, all created before the scheduler starts
  • HWLINK over UART: COBS framing, CRC-32, verified FlatBuffers, replay of the last reply
  • Health task owns the watchdog; every task must check in, or the board resets
  • Writes the bootloader's CONFIRMED record, its only flash write
  • Fault capture: reset cause, CFSR/HFSR/PC/LR, stack high-water marks and heap stats
  • LED patterns and debounced button events, controlled from the host
  • Footprint gate in the build: fails above 128 KB flash or 64 KB RAM

  2. ServicesHWLINK · watchdog · fault record
  3. FreeRTOS kernelqueues · notifications · static allocation

03RTOS · Zephyr

Zephyr application on Zephyr 4.4

The same application built the Zephyr way, with devicetree, Kconfig and threads, for products that need a full OS with drivers and networking. It uses the same slot, protocol and health contract as the others.

C · Zephyr 4.4.2Implemented

Features

  • Devicetree overlay whose flash partitions match the bootloader layout
  • Clock and caches set up from devicetree and Kconfig
  • Interrupt-driven HWLINK on UART; malformed or unknown frames get a clear NAK
  • Health thread as the only watchdog feeder; other threads check in through a k_event
  • Fatal-error record for faults, assertions and stack overflows
  • Freestanding CMake build without a west workspace, in a Docker image

04Rust · FreeRTOS

Rust application on FreeRTOS

The same application in no_std Rust, with its tasks running on the FreeRTOS kernel. It is being ported from the existing Embassy build, which already meets the same specification and bootloader contract as the C version.

Rust · FreeRTOS · no_stdPorting from Embassy

Features

  • Rust tasks on the FreeRTOS kernel through FFI bindings, statically allocated
  • Same HWLINK protocol, with a fixed-buffer FlatBuffers codec verified against flatc
  • Health task with watchdog ownership, task check-ins and the CONFIRMED record
  • Fault record, reset cause and status reporting, the same as the C version
  • Builds the bootloader image file directly
  • Rust toolchain, clippy and rustfmt in a Docker image; crates locked in Cargo.lock

05Rust · Zephyr

Rust application on Zephyr

The same application written in no_std Rust on Zephyr 4.4, with Zephyr's own Rust support for threads, GPIO and flash. A small C layer covers the drivers the Rust bindings do not reach yet. It uses the same slot, protocol and health contract as the others.

Rust · Zephyr 4.4.2 · no_stdImplemented · bench test pending

Features

  • Four Rust threads with the C Zephyr version's priorities; no allocator
  • Same HWLINK protocol and fixed-buffer FlatBuffers codec as the Embassy build
  • Health thread as the only watchdog feeder, with the CONFIRMED record
  • Fault record for CPU faults, stack overflows and Rust panics, shown on LD3
  • Thin C layer for UART, watchdog and the fatal handler, mirroring the C Zephyr version
  • Docker build on the Zephyr image; rustfmt and clippy in CI

06Validation · Firmware

HWVAL, the validation firmware

FreeRTOS firmware that tests every usable hardware block of the STM32F767ZI and the NUCLEO board, both at bring-up and before each board ships. It runs from a terminal or under the desktop and factory apps.

C · FreeRTOS · LwIPFeature-complete

Features

  • 201 test cases in 49 groups: CPU, clocks, memory, ADC/DAC, timers, UART, SPI, I2C, CAN, USB, Ethernet and more
  • Three levels: standalone, harness-wired and full bench with test equipment
  • Operator prompts for buttons, LEDs and anything a person must confirm
  • Text CLI for people, a script mode with JSON, and HWLINK link mode for the apps
  • Host script that writes JSON and Markdown reports per board
  • Build gates for footprint, requirement coverage and cppcheck; warnings are errors
  • Written to an SRS; every requirement maps to a test

07Validation · GUI

HWVAL Studio, the bench app

A cross-platform desktop app for macOS, Windows and Linux. It runs the HWVAL tests, shows operator prompts, keeps the run history, updates firmware through the bootloader and flashes over SWD, all without typing commands.

Python · PySide6 · SQLiteImplemented · v0.1.0

Features

  • Test catalogue read from the board, with search, levels, repeat-until-fail and live results
  • Operator prompt sheets and a simplified operator mode with an optional PIN
  • UART update: A/B slot view, image and CRC checks, progress, activation and confirmation watch
  • SWD flashing and option-byte display through OpenOCD and ST-LINK
  • Run history in SQLite with compare and CSV/JSON export; reports in JSON, Markdown and PDF
  • Built-in device simulator, so it works without hardware
  • Headless CLI with pass/fail exit codes for CI

08Factory Provisioning

HWVAL Factory, test and provisioning

The end-of-line station for the factory floor. In one operator action per board it is designed to flash and test the board, give it its identity, program the product, apply flash protection, print the label and keep the record. It runs up to eight fixtures per PC; the hardware integration is still in development.

Python · PySide6 · OpenOCDIn development · v0.1.0

Features

  • Product profiles with SHA-256-pinned images and Ed25519 signatures; no code changes per product
  • One worker, OpenOCD process and state machine per fixture, with independent start and abort
  • Serial number and MAC allocation, and a provisioning record read back byte for byte
  • Option bytes, write and readout protection, with RDP level 2 always refused
  • ZPL labels, a per-unit PDF certificate and an optional queued MES uplink
  • Operator, supervisor, engineer and admin roles; yield dashboard with Pareto
  • Fixture simulator and packaging for Windows (MSI) and Linux (.deb, AppImage)
