01Bootloader

A/B bootloader, updates that can't brick

A new image goes into the inactive slot, is verified, trial-booted, and kept only when the application confirms it is healthy. If it isn't, the bootloader rolls back automatically — updates can't brick the board.

B.01 · Bare metal · CSkeleton · builds

What it will do

  • Two slots, one per flash bank, so the running image is never overwritten
  • Image header with version and size, checked with CRC32 before activation
  • Trial boot with a boot counter and automatic rollback to the last good image
  • Firmware upload over UART using the HWLINK host protocol
  • Small: 32 KB, no RTOS, no dynamic memory

Skeleton today: flash-mode check, slot A vector check and hand-over work. UART update, A/B selection and rollback are next.

Adapted to your flash map and update path: UART, USB, CAN or Ethernet.

02Application · C/C++

Applications in C/C++

The language most STM32 products ship in. I work bare metal on HAL/LL or on an RTOS, with the bootloader contract built in from day one.

A.01 · C/C++ · FreeRTOSSkeleton · builds

What it will do

  • 216 MHz clock tree, MPU and caches, fault handlers, watchdog
  • Drivers on DMA and interrupts: UART, SPI, I2C, CAN, ADC, timers
  • Health check that confirms a new image to the bootloader
  • HWLINK host protocol for status, logs and updates

06Validation · Firmware

Validation firmware

Firmware that tests every usable block of the chip and the board, so you know the hardware works before the application is written — and again before each board ships.

V.01 · C · FreeRTOSFeature-complete

What it covers

  • 201 test cases in 49 groups: CPU, memory, clocks, analog, communication, RTOS and more
  • Three levels: standalone (under 15 min), harness-wired, and full bench with operator prompts
  • Operator prompts for buttons, LEDs and anything a person must confirm
  • Scriptable CLI over UART, with text and JSON reports
  • Requirements in an SRS; every requirement mapped to a test

Feature-complete against its SRS. Bench validation is the next step.

08End-of-line

End-of-line test and provisioning

A station tool for the factory floor: every board is flashed, tested, given its identity and locked, and the record is kept.

E.01 · HWVAL Factory · PythonSpecified

Factory automation

  • Flow engine driven by product profiles, not code changes
  • Up to eight fixtures per PC, with simple screens for operators
  • Serial number and MAC allocation, written to the device
  • Readout and write protection set before the board leaves
  • ZPL labels and a full provisioning record for traceability

Specification and default flow defined. Implementation has not started.
