Why Lyra exists

After 25 years in embedded software, the last 10 as a consultant, I kept rebuilding the same foundations on every project: bootloader, secure updates, drivers, RTOS setup and factory tooling. Weeks of work before the real product could even start.

Lyra is those foundations for STM32 microcontrollers, built once and reused: a secure bootloader with rollback, working applications on three runtimes and the tools to flash and test boards on the line. It shares its architecture with the other 9 platforms, so what you learn here carries to every other board.

Get started

The bootloader is the best place to begin. The reference build targets the STM32F767ZI; it builds in a container and flashes over SWD with an ST-LINK.

git clone https://github.com/soccentric-lyra/bootloader.git
cd bootloader
scripts/build.sh     # build inside the stm32-dev container
make flash           # flash build/boot.elf over SWD
make test            # host, Python and contract tests

Then flash any demo application into either slot. Full steps are in the bootloader README.

Inside the platform

What each repository provides.

Bootloader

bootloader

C · bare-metal

  • Dual-bank A/B layout with two 976 KB application slots in the STM32F7 flash
  • Signed images: ECDSA P-256, checked before an update erases anything and on every boot
  • Anti-rollback security counter, with no OTP or option-byte writes
  • Trial boot with a watchdog and automatic rollback after three failed starts
  • Image updates over UART with HWLINK, in about 28 KB of flash

bootloader-gui

Python · PySide6

  • Desktop GUI that builds the bootloader and flashes it over SWD
  • Clones, builds, signs and uploads the firmware projects through the bootloader
  • Board panel with the bootloader version, slots, trusted key and security floor
  • Live debug terminal on USART6 beside the flash output
  • Recover Board into BOOT when the running application does not answer

Applications

app-c-freertos

C · FreeRTOS

  • Runs from either bootloader slot, with seven LED patterns and a debounced user button
  • HWLINK over USART3 with COBS framing, CRC-32 and FlatBuffers
  • Four tasks, with a health task as the only watchdog feeder
  • Writes the CONFIRMED record after a successful trial health check
  • Static allocation only, reproducible Docker build

app-c-zephyr

C · Zephyr

  • Devicetree overlay that matches the bootloader flash layout
  • Same job as the C FreeRTOS demo: LED patterns, button and HWLINK
  • Health thread supervises the others and feeds the watchdog
  • Captures faults, assertions and stack overflows into no-init RAM
  • Build enforces a 128 KB flash and 64 KB RAM budget

app-rust-embassy

Rust · Embassy

  • Pure Rust, no_std and no allocator, on the Embassy async executor
  • Four async tasks: health, comms, button and LED
  • HWLINK at 115200 or 921600 baud with a fixed-buffer FlatBuffers codec
  • Fault record kept in a no-init RAM window that survives every reset
  • Pinned Rust toolchain in a reproducible Docker build

app-rust-freertos

Rust · FreeRTOS

  • All application logic in Rust, no_std and no allocator, on the FreeRTOS kernel
  • C keeps the board start-up, STM32 HAL drivers and bootloader contract
  • CMake links the Rust static library after the C objects into one image
  • Same job as the C FreeRTOS demo, from either bootloader slot
  • Watchdog supervision and self-confirmation after a health check

app-rust-zephyr

Rust · Zephyr

  • Application logic in Rust on Zephyr's official Rust module
  • Thin C glue for USART3, watchdog, reboot and the flash partition
  • Four Zephyr threads defined with the zephyr thread attribute
  • CPU faults, stack overflows and Rust panics captured into no-init RAM
  • rustfmt and clippy checks with warnings as errors

Factory

factory-firmware

C · FreeRTOS

  • First application a fresh board runs after the bootloader is flashed
  • Linked for slot A and answers the factory station over the ST-LINK virtual COM port
  • Writes per-unit system info, calibration data and the diagnostic map
  • Reports its name and version to the station
  • Derived from the C FreeRTOS demo, with its health supervision and watchdog

factory-station

Python · PySide6

  • Takes a blank board from the box to a verified unit, one page at a time
  • Eight bench actions: detect, load BOOT, load factory firmware, info, SYS, CAL, DIAG and validate
  • Generates the system, calibration and diagnostic files from CSV
  • Unit registry that only moves forward, from planned to shipped, RMA or scrapped
  • Simulated board for every action, so no hardware is needed
