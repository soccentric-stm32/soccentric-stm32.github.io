01Bootloader · Firmware

Bootloader

A bare-metal bootloader with two application slots. A new image is checked, tried on trial and kept only when the application confirms it is healthy; otherwise it rolls back to the last good image. A starting point for a secure update path, built in Docker.

Bare metal · C

Features

  • Dual-bank A/B slots: two application images; the last good one is always kept
  • Signed images: ECDSA P-256, checked before any erase and on every boot
  • Anti-rollback: a security counter in the signed header; no OTP or option bytes
  • Trial boot: watchdog-supervised; three failed starts roll back
  • Power-loss-safe records: append-only metadata survives an interrupted update
  • Lazy sector erase: only the sectors an update touches are erased
  • Updates over UART: a framed, checksummed protocol with a status reply
  • Python host tools: mkimage.py signs and inspects images, bootctl.py updates devices, and boards can be provisioned over SWD
  • Tests without hardware: host C tests on a simulated flash; Python protocol tests
  • Docker build: portable and reproducible; optional hardware-in-the-loop CI test

02Bootloader · GUI

Bootloader GUI

A desktop app for the bootloader. It builds and flashes the bootloader, then builds, signs and uploads your firmware, so nobody has to remember command lines. A starting point for your own flashing and release tooling.

Python · PySide6

Features

  • One window: build, sign and flash without command lines
  • A full pipeline: clone, build, sign and upload each firmware project
  • Docker or host builds: falls back to Docker when the vendor SDK is missing
  • Offline signing: choose the signing key; no network needed
  • A board panel: version, both slots, trusted key and security floor
  • SWD buttons: program, provision, reset and erase the board
  • A live debug terminal: stays open while the board is being flashed
  • A recovery path: gets a board back into the bootloader when the app is silent
  • Light and dark themes: follow the system; keyboard shortcuts for the pipeline
  • Python and PySide6: a thin front-end over the bootloader's own tools, with tests

03RTOS · FreeRTOS

C / FreeRTOS

FreeRTOS is already configured, with tasks, watchdog supervision and fault handling in place, and a Docker build that makes a ready-to-flash image. Add your features instead of building the foundation.

C · FreeRTOS · STM32CubeF7

Features

  • Docker build: a reproducible toolchain that makes a ready-to-flash image
  • FreeRTOS configured: four tasks (health, comms, button, LED) to add to
  • Static allocation: nothing is allocated after the scheduler starts
  • Watchdog supervision: one health task feeds it; a stuck task resets the device
  • A fault record: fault details survive a reset for the next boot
  • A host protocol: a framed, checksummed link to a desktop tool
  • Runtime statistics: task stack and heap use reported to the host
  • A fail-health option: force a failed start to test rollback on purpose
  • Build gates: the build fails if the image outgrows its flash and RAM budget
  • Written to a spec: requirements are documented, and CI runs the build and static analysis

04RTOS · Zephyr

C / Zephyr

Zephyr is already configured for the board, with devicetree and Kconfig set up, watchdog supervision and a pinned Docker build. For products that want a full OS with drivers and networking.

C · Zephyr 4.4.2

Features

  • Zephyr configured: devicetree and Kconfig set up for the board
  • Docker build: a pinned Zephyr environment; no west workspace to manage
  • Threads to add to: health, comms, button and LED threads in place
  • Interrupt-driven UART: receive and transmit without polling
  • Watchdog supervision: one health thread feeds it
  • Fault capture: faults, asserts and stack overflows kept across a reset
  • A host link: bad requests get a NAK; repeats are replayed
  • A Kconfig failure option: force a rollback to test it
  • A clear structure: source grouped by responsibility, dependencies one way
  • A budget gate: the build enforces a flash and RAM budget

05Rust · Embassy

Rust / Embassy

A pure no_std Rust application on the Embassy async executor, with its tasks, watchdog supervision and a pinned Rust toolchain in Docker already in place. Use it to start a new Rust project or to move toward Rust.

Rust · Embassy · no_std

Features

  • Pure Rust: no_std with no allocator, on the Embassy executor
  • Async tasks: four (health, comms, button, LED) to add to
  • Docker build: a pinned Rust toolchain with crate versions locked
  • Watchdog supervision: one feeder, with health check-ins
  • A fault record: kept in reserved RAM that survives every reset
  • A host link: framing and checksums that match the C code
  • Button handling: external interrupt with debounce; short and long presses
  • Fixed buffers: the protocol codec is checked against the reference encoder
  • Works with our bootloader: runs from either slot of the A/B bootloader
  • Checked in CI: clippy and codec tests run on every change

06Rust · FreeRTOS

Rust / FreeRTOS

Application logic in Rust on the FreeRTOS kernel you already trust, with start-up and drivers kept in C and one CMake build for both. The pattern for moving an existing C product to Rust step by step.

Rust · FreeRTOS · no_std

Features

  • Rust application logic: no_std, no heap, on the FreeRTOS kernel
  • A thin C platform layer: start-up, HAL drivers and FreeRTOS setup stay in C
  • One CMake build: compiles the C and Rust into a single image
  • Docker build: a reproducible environment for both languages
  • Four tasks: created before the scheduler starts; ready to add to
  • One fault path: Rust panics, asserts and stack overflows converge
  • Watchdog supervision: the health task is the only feeder
  • A fault record: fault details survive a reset
  • A documented split: requirements and architecture notes cover the C and Rust boundary
  • A budget gate: the build fails if the image outgrows its flash and RAM budget

07Rust · Zephyr

Rust / Zephyr

Application logic in Rust on Zephyr 4.4, using Zephyr's own Rust support, with a small C layer for what the bindings do not cover yet. Devicetree and Kconfig stay as they are, and the build runs in Docker.

Rust · Zephyr 4.4.2 · no_std

Features

  • Zephyr's official Rust module: threads, GPIO and flash called from Rust
  • Rust application logic: no_std with no allocator
  • Thin C glue: UART, watchdog, reboot, flash and fault handler where bindings are missing
  • Four threads in Rust: ready to add to
  • Docker build: a pinned Zephyr and Rust environment
  • Fault capture: CPU faults, stack overflows and panics kept across a reset
  • Interrupt-driven UART: receive and transmit without polling
  • Kconfig in Rust: Kconfig options exported to Rust as cfg flags
  • Strict checks: rustfmt and clippy, with warnings treated as errors
  • A shared codec: the same host-link codec as the Embassy build

08Validation · Firmware

Validation firmware

A starting point for proving a board works. Ready-made tests for the hardware blocks of the STM32F767ZI and its board, from clocks and timers to serial buses, Ethernet and memory. You add the tests for your own hardware.

C · FreeRTOS · LwIP

Features

  • Tests for every hardware block: grouped by block, on the MCU and the board
  • Core, clocks and power: Cortex-M7 and FPU, faults, clocks and PLLs, power modes
  • Timers, DMA, RTC, watchdogs: plus interrupts, caches and the MPU
  • Serial and buses: UART, SPI, I2C, I2S, SAI, CAN and USB
  • Ethernet: ping, TCP and UDP tests on LwIP
  • GPIO, ADC and DAC: pins, analog inputs and analog outputs
  • Memory: internal flash, RAM, QSPI, FMC, SD card, option bytes and OTP
  • Display, camera, debug: LTDC, DCMI, DMA2D and JPEG; debug and trace
  • Console, script or GUI: reports in JSON and Markdown for every board
  • Traced and reproducible: every test maps to a requirement; built in Docker

09Validation · GUI

Validation GUI

A desktop app for macOS, Windows and Linux that runs the HWVAL tests, shows the results live, and keeps a history of runs and reports. A built-in simulator means it works without a board.

Python · PySide6 · SQLite

Features

  • Runs the HWVAL tests: single, group or full runs, with repeat and run-until-fail
  • A test catalogue: read from the firmware, with search and filters
  • Live results and prompts: operator prompts for tests that need a human
  • Run history in SQLite: compare, filter and export to CSV or JSON
  • Reports: JSON, Markdown and PDF
  • Firmware update: through the A/B bootloader, with downgrade warnings
  • SWD flashing: flash and provision through OpenOCD with live output
  • A built-in simulator: plus a TCP simulator server for other tools
  • A headless command line: pass, fail and comms exit codes for CI
  • Operator mode: simplified, with an optional PIN; macOS, Windows and Linux

10Factory · Firmware

Factory firmware

A starting point for the first firmware on a fresh board. A small FreeRTOS app, built in Docker, that the factory station flashes in. It writes each unit's identity, calibration and diagnostic data into a protected area of flash.

C · FreeRTOS · UART

Features

  • The first app on a board: flashed into slot A after the bootloader, signed with your key
  • Reports itself: name, version, build date and chip ID
  • Three protected data blocks: system info, calibration and diagnostics
  • UART commands: info, read, a staged write and diagnostics init
  • Header and checksum checks: done before anything touches flash
  • Chip binding: data for one chip is refused on any other
  • Read-back: every programmed block is read back
  • A write guard: writes outside the three blocks are refused
  • A FreeRTOS base: health supervision and watchdog; built in Docker
  • Host tests: the real command handler runs on a simulated flash

11Factory · Station

Factory station

A starting point for your production station. It takes a blank board to a finished unit in one guided flow: it programs the board, writes the unit's data, runs a self-test and records the result. A simulator runs every step without hardware; the hardware side is still in development.

Python · PySide6 · OpenOCD

Features

  • A guided flow: from a blank board to a provisioned unit
  • Probe and port detection: finds ST-LINK probes and UART ports
  • Bootloader over SWD: programmed after the dual-bank option bytes are set
  • Signed factory firmware: installed through the bootloader with your key
  • Per-unit data: system info from a CSV database; calibration and diagnostics over UART
  • Read-back checks: every write is read back and compared
  • Identity protection: an address check guards the device identity record
  • A validation page: self-test of chip, flash, clock and RAM, with a saved report
  • Up to eight fixtures: in parallel on one PC; a full simulator runs every step
  • PIN login by role: SQLite database; automated tests and lint for the station

12Factory · Data GUI

Factory data GUI

A desktop app that converts per-unit calibration, diagnostic and system data from a spreadsheet into the exact memory image the firmware stores in flash. It checks every record first and keeps the CSVs and files together in Git.

Python · PySide6

Features

  • CSV in, files out: system info, calibration and diagnostics for every unit
  • The device's memory image: converts the data into the exact format the firmware stores
  • Four pages: system info, calibration, diagnostics and inspect
  • Line-by-line checks: the exact CSV line of every problem
  • Sanity warnings: for values that are legal but suspicious
  • A manifest: size and checksums for every generated file
  • Verify Folder: reports files that changed, are missing or were never generated
  • Optional chip binding: a file is accepted by one chip only
  • A batch tool: counting id, serial and MAC for a run of units
  • Git built in: CSVs and outputs kept together; pull, commit and push from the app
