01Bootloader · GUI

BOOT Flasher, one app from build to board

A desktop app that builds the bootloader and programs it over SWD, then clones, builds, signs and uploads each firmware project through it. The board's slots, trusted key and security floor are checked before anything is written.

Python · PySide6Implemented

What's in the repo

Build environment
Python and PySide6. make deps, then make gui.
What you get
Build, sign and install firmware from one window, with no commands to type.
Architecture
A thin front-end over the bootloader's own command-line tools.
Design
One pipeline per project: clone, build, sign, flash. Each step also runs alone.
Implementation
A job runner for the tools, a light and dark theme, and a project model.
Test & validation
Python tests for the project model and board info; compile check on every build.
App features
Board panel, key and counter warnings, and recovery of a board that does not answer.

02Bootloader · Firmware

A/B bootloader, updates that can't brick

A bare-metal bootloader with two application slots, one in each flash bank. A new image is written to the inactive slot, verified, trial-booted and kept only when the application confirms it is healthy. Otherwise the bootloader rolls back to the last good image.

Bare metal · CFeature-complete · v0.1

What's in the repo

Build environment
Docker toolchain with GCC, CMake and Ninja. The build fails if BOOT outgrows 32 KB.
What you get
Updates that cannot brick the board: try the new version, roll back if it misbehaves.
Architecture
Two application slots in dual-bank flash; one binary runs from either slot.
Design
Trial boot under a watchdog, rollback after three failed starts, signed images only.
Implementation
Bare-metal C in about 28 KB. No RTOS, no dynamic memory, updates over UART.
Test & validation
Host tests on a simulated flash, protocol tests and a hardware rollback test.
Host tools
bootctl.py to update, mkimage.py to sign, provision.sh for a new board.

03RTOS · FreeRTOS

FreeRTOS application in C/C++

The reference application and the template for new products. It runs under the A/B bootloader, talks to the host over HWLINK, supervises its own tasks and confirms a new image only after a health check.

C · FreeRTOS · STM32CubeF7Feature-complete

What's in the repo

Build environment
Docker toolchain. The build enforces a 128 KB flash and 64 KB RAM budget.
What you get
The reference application and the template for a new product.
Architecture
Four FreeRTOS tasks: Health, Comms, Button and LED. Runs from either slot.
Design
One task feeds the watchdog; an update is confirmed only after a health check.
Implementation
C with static allocation only; nothing is allocated once the scheduler starts.
Test & validation
CI runs build, static analysis, boot-contract and image checks. Written to an SRS.
App features
Seven LED patterns, a debounced button and nine host commands with a status reply.

04RTOS · Zephyr

Zephyr application on Zephyr 4.4

The same application built the Zephyr way, with devicetree, Kconfig and threads, for products that need a full OS with drivers and networking. It uses the same slot, protocol and health contract as the others.

C · Zephyr 4.4.2Implemented

What's in the repo

Build environment
Docker image with Zephyr and its SDK pinned. Same 128 KB / 64 KB budget.
What you get
The same product on Zephyr, so you can compare the two kernels before choosing.
Architecture
A devicetree overlay matches the bootloader layout; source grouped by responsibility.
Design
One thread feeds the watchdog; bad requests get a NAK, repeats are replayed.
Implementation
C on Zephyr with interrupt-driven UART and fault capture into no-init RAM.
Test & validation
CI runs build, boot-contract and image checks; a Kconfig option forces a rollback.
App features
LED patterns, button, baud switch to 921600 with fallback, and a status reply.

05Rust · Embassy

Rust application on Embassy

Many companies are moving from C/C++ to Rust for memory safety and modern tooling—we help port existing projects or start new ones across three popular Rust frameworks: Embassy, FreeRTOS and Zephyr. This build runs in no_std Rust on the Embassy async executor under the A/B bootloader, with four async tasks, HWLINK, watchdog supervision and health confirmation.

Rust · Embassy · no_stdFeature-complete

What's in the repo

Build environment
Docker image with a pinned Rust toolchain and locked crate versions.
What you get
The same product in pure Rust: memory safety and async tasks without a heap.
Architecture
no_std Rust on the Embassy executor with four async tasks.
Design
The same boot contract as the C versions: one watchdog feeder, confirm after trial.
Implementation
No allocator. Framing and CRC shared with the C code; fixed-buffer codec.
Test & validation
Codec verified against the reference encoder. CI runs build, clippy and format.
App features
LED patterns, EXTI button, host link at 115200 or 921600 baud, button events.

app-rust-embassy on GitHub ↗

06Rust · FreeRTOS

Rust application on FreeRTOS

The same application written in no_std Rust, with its tasks running on the FreeRTOS kernel and driven from Rust through a thin C platform layer. It uses the same slot, HWLINK protocol and health contract as the C FreeRTOS version.

Rust · FreeRTOS · no_stdImplemented · bench test pending

What's in the repo

Build environment
Docker image with pinned Rust. One CMake build compiles and links C and Rust.
What you get
Keep the FreeRTOS kernel and drivers you trust; write the application in Rust.
Architecture
A C platform layer under Rust application logic, linked as a static library.
Design
Rust panics, FreeRTOS asserts and stack overflows all take one fault path.
Implementation
no_std Rust with no allocator; C covers GPIO, UART, watchdog and flash.
Test & validation
CI runs build, static analysis, format and boot-contract checks. Bench validation pending.
App features
The same demo as the C version: LEDs, button, host commands and status.

07Rust · Zephyr

Rust application on Zephyr

The same application written in no_std Rust on Zephyr 4.4, with Zephyr's own Rust support for threads, GPIO and flash. A small C layer covers the drivers the Rust bindings do not reach yet. It uses the same slot, protocol and health contract as the others.

Rust · Zephyr 4.4.2 · no_stdImplemented · bench test pending

What's in the repo

Build environment
Docker image for Zephyr 4.4 with Rust. Same 128 KB / 64 KB budget.
What you get
Rust on a mainstream RTOS, with devicetree and Kconfig kept as they are.
Architecture
Zephyr's official Rust module; four threads; a small C layer fills the gaps.
Design
The same watchdog and trial contract; the Kconfig test option reaches Rust as a flag.
Implementation
no_std Rust in about 45 KB of flash and 35 KB of RAM.
Test & validation
rustfmt and clippy with warnings as errors, plus build and boot-contract checks.
App features
The same demo; the host-link codec is shared with the Embassy build.

08Validation · Firmware

HWVAL, the validation firmware

FreeRTOS firmware that tests every usable hardware block of the STM32F767ZI and the NUCLEO board, both at bring-up and before each board ships. It runs from a terminal or under the desktop and factory apps.

C · FreeRTOS · LwIPFeature-complete

What's in the repo

Build environment
Docker toolchain. Footprint gate, strict cppcheck and warnings as errors.
What you get
Know a new board is good before firmware work starts, with a report per board.
Architecture
FreeRTOS firmware with 196 tests, driven from a console, a script or the GUI.
Design
Three test levels, operator prompts, and destructive tests kept to a reserved sector.
Implementation
C on FreeRTOS with LwIP for Ethernet, plus USB, SWO and watchdog checks.
Test & validation
Written to an SRS; CI checks that every requirement has a test.
Console
run, list, report and tasks; JSON and Markdown reports from hwtest.py.

09Validation · GUI

HWVAL Studio, the bench app

A cross-platform desktop app for macOS, Windows and Linux. It runs the HWVAL tests, shows operator prompts, keeps the run history, updates firmware through the bootloader and flashes over SWD, all without typing commands.

Python · PySide6 · SQLiteImplemented · v0.1.0

What's in the repo

Build environment
Python, PySide6 and SQLite. Packaged for macOS, Windows and Linux.
What you get
Run the hardware tests, watch results live and export reports, with or without a board.
Architecture
A desktop app with a built-in device simulator and a headless CLI for CI.
Design
Tests grouped by hardware block; operator mode with prompts and an optional PIN.
Implementation
Run history in SQLite with compare; reports in JSON, Markdown and PDF.
Test & validation
Written to an SRS. CI runs lint, type checks, a CLI smoke test and the test suite.
App features
UART update with an A/B slot view, SWD flashing, run history and reports.

10Factory · Station

HWVAL Factory, test and provisioning

The end-of-line station for the factory floor. In one operator action per board it is designed to flash and test the board, give it its identity, program the product, apply flash protection, print the label and keep the record. It runs up to eight fixtures per PC; the hardware integration is still in development. Bench pages take a blank board from the box to a unit with its system info, calibration and diagnostic map.

Python · PySide6 · OpenOCDIn development · v0.1.0

What's in the repo

Build environment
Python and PySide6. A full simulator runs every step without hardware.
What you get
One operator action per board: test, program, identify, protect, label and record.
Architecture
One module per step; up to eight fixtures run in parallel on one PC.
Design
Product profiles, PIN login by role, work orders and a traceable record per unit.
Implementation
SQLite database, SWD flashing through OpenOCD and the shared host-link stack.
Test & validation
CI runs lint, type checks, a station self-test and the suite; optional hardware stage.
App features
Bench pages for a blank board: detect, flash, device info, calibration, diagnostics.

factory-station on GitHub ↗

11Factory · Firmware

Factory firmware, the first app on a fresh board

A FreeRTOS application in C that the factory station flashes into slot A right after the bootloader. It reports its name and version, then stores the unit's system info, calibration and diagnostic map in the board when the station sends them over UART.

C · FreeRTOS · UARTIn development · v0.1.0

What's in the repo

Build environment
Docker toolchain. The station signs the built image with your key.
What you get
The first application on a fresh board; it stores each unit's identity data.
Architecture
Runs from slot A; three 4 KB blocks hold system info, calibration and diagnostics.
Design
Writes outside its three blocks are refused, so the identity record stays safe.
Implementation
FreeRTOS in C. Checks headers, CRCs and the chip UID, then writes and reads back.
Test & validation
Host tests run the real command handler against a simulated flash.
Commands
INFO, READ, WRITE_BEGIN/DATA/END and DIAG_INIT over UART.

12Factory · Data GUI

Factory Data, CSV to unit files

A desktop app that turns CSV files into the .sys, .cal and .diag factory data files for each unit. They are the same files the factory station writes and the factory firmware stores, so a unit's identity, calibration and diagnostic map can be prepared ahead of the line.

Python · PySide6Implemented

What's in the repo

Build environment
Python 3.10+ and PySide6. The file format and CSV loaders need only the standard library.
What you get
One file per unit for system info, calibration and diagnostics, from a spreadsheet.
Architecture
A Qt-free core package holds the format and generators; the GUI sits on top.
Design
Rows of one id make one file; shared rows apply to every unit; an optional chip UID binds a file to one chip.
Implementation
A 32-byte header with two CRC-32s, then a TLV payload of at most 4096 bytes.
Test & validation
Python tests cover the format and the CSV loaders.
App features
Preview records, write one or all, sample CSVs, and an Inspect page that checks CRCs and lists items.
