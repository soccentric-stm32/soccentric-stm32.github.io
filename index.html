01Bootloader · Firmware

Bootloader

A bare-metal A/B bootloader with signed, rollback-protected updates. Each new image is verified, booted on trial and committed only once the application confirms it is healthy; otherwise the device reverts to the last known-good image. A foundation for a secure update path, with a reproducible Docker build.

Bare metal · C

Features

  • Dual-bank A/B slots: two image slots, with the last known-good image always retained
  • Signed images: ECDSA P-256 signatures verified before any erase and again on every boot
  • Anti-rollback: a security counter in the signed header, with no OTP or option-byte dependency
  • Trial boot: watchdog-supervised, with automatic rollback after three failed starts
  • Power-loss-safe metadata: append-only records survive an interrupted update
  • Minimal erase: only the sectors an update touches are erased
  • UART updates: a framed, checksummed protocol with an explicit status reply
  • Python host tools: mkimage.py signs and inspects images, bootctl.py updates devices, and boards can be provisioned over SWD
  • Hardware-free tests: host C tests on simulated flash, plus Python protocol tests
  • Reproducible Docker build: a portable toolchain, with an optional hardware-in-the-loop CI test

02Bootloader · GUI

Bootloader GUI

A desktop application for the bootloader. It builds and flashes the bootloader, then builds, signs and uploads your firmware, replacing a chain of command-line steps with one guided workflow. A foundation for your own flashing and release tooling.

Python · PySide6

Features

  • Single workspace: build, sign and flash without touching a command line
  • End-to-end pipeline: clone, build, sign and upload each firmware project
  • Docker or host builds: falls back to Docker when the vendor SDK is unavailable
  • Offline signing: select your signing key; no network access required
  • Board status panel: version, both slots, trusted key and security floor
  • SWD controls: program, provision, reset and erase the board
  • Live debug terminal: stays connected throughout flashing
  • Recovery path: returns a board to the bootloader when the application is unresponsive
  • Light and dark themes: follow the system setting, with keyboard shortcuts for the pipeline
  • Python and PySide6: a thin, tested front end over the bootloader's own tools

03RTOS · FreeRTOS

C / FreeRTOS

A pre-configured FreeRTOS application with tasks, watchdog supervision and fault handling already in place, and a Docker build that produces a flash-ready image. Start from a working base and spend your time on the product.

C · FreeRTOS · STM32CubeF7

Features

  • Docker build: a reproducible toolchain that produces a flash-ready image
  • FreeRTOS pre-configured: four tasks (health, comms, button, LED) ready to extend
  • Static allocation: no heap allocation once the scheduler starts
  • Watchdog supervision: a single health task feeds it, so a stuck task resets the device
  • Fault record: crash details persist across a reset for the next boot
  • Host protocol: a framed, checksummed link to desktop tooling
  • Runtime statistics: task stack and heap usage reported to the host
  • Fail-health option: force a failed start to exercise rollback deliberately
  • Build gates: the build fails if the image exceeds its flash or RAM budget
  • Specification-driven: documented requirements, with CI running the build and static analysis

04RTOS · Zephyr

C / Zephyr

A pre-configured Zephyr application for the board, with devicetree, Kconfig, watchdog supervision and a pinned Docker build. Suited to products that need a full operating system with a driver ecosystem and networking.

C · Zephyr 4.4.2

Features

  • Zephyr pre-configured: devicetree and Kconfig set up for the board
  • Docker build: a pinned Zephyr environment, with no west workspace to maintain
  • Extensible threads: health, comms, button and LED threads in place
  • Interrupt-driven UART: receive and transmit without polling
  • Watchdog supervision: a single health thread feeds it
  • Fault capture: faults, asserts and stack overflows persist across a reset
  • Host link: malformed requests receive a NAK, and repeated requests are replayed
  • Kconfig failure option: force a rollback to test it
  • Clear structure: source grouped by responsibility, with one-way dependencies
  • Budget gate: the build enforces a flash and RAM budget

05Rust · Embassy

Rust / Embassy

A pure no_std Rust application on the Embassy async executor, with tasks, watchdog supervision and a pinned toolchain in Docker. The starting point for a new Rust product, or for moving an existing one to Rust.

Rust · Embassy · no_std

Features

  • Pure Rust: no_std with no allocator, on the Embassy executor
  • Async tasks: four (health, comms, button, LED) ready to extend
  • Docker build: a pinned Rust toolchain with locked crate versions
  • Watchdog supervision: a single feeder, driven by health check-ins
  • Fault record: stored in reserved RAM that persists across resets
  • Host link: framing and checksums identical to the C implementation
  • Button handling: external interrupt with debounce, distinguishing short and long presses
  • Fixed buffers: the protocol codec is verified against the reference encoder
  • Bootloader-ready: runs from either slot of the A/B bootloader
  • Continuous integration: clippy and codec tests run on every change

06Rust · FreeRTOS

Rust / FreeRTOS

Application logic in Rust on the FreeRTOS kernel you already rely on, with start-up and drivers kept in C and a single CMake build for both languages. An incremental migration path for an existing C product.

Rust · FreeRTOS · no_std

Features

  • Rust application logic: no_std, no heap, on the FreeRTOS kernel
  • Thin C platform layer: start-up, HAL drivers and FreeRTOS setup remain in C
  • Single CMake build: compiles the C and Rust into one image
  • Docker build: a reproducible environment for both languages
  • Four tasks: created before the scheduler starts, ready to extend
  • Unified fault path: Rust panics, asserts and stack overflows converge on one handler
  • Watchdog supervision: the health task is the sole feeder
  • Fault record: crash details persist across a reset
  • Documented boundary: requirements and architecture notes cover the C and Rust split
  • Budget gate: the build fails if the image exceeds its flash or RAM budget

07Rust · Zephyr

Rust / Zephyr

Application logic in Rust on Zephyr 4.4 using Zephyr's official Rust support, with a thin C layer where bindings do not yet exist. Devicetree and Kconfig are used unchanged, and the build runs in Docker.

Rust · Zephyr 4.4.2 · no_std

Features

  • Official Zephyr Rust module: threads, GPIO and flash driven from Rust
  • Rust application logic: no_std with no allocator
  • Thin C glue: UART, watchdog, reboot, flash and fault handler where bindings are not yet available
  • Four Rust threads: ready to extend
  • Docker build: a pinned Zephyr and Rust environment
  • Fault capture: CPU faults, stack overflows and panics persist across a reset
  • Interrupt-driven UART: receive and transmit without polling
  • Kconfig integration: Kconfig options exported to Rust as cfg flags
  • Strict checks: rustfmt and clippy, with warnings treated as errors
  • Shared codec: the same host-link codec as the Embassy build

08Validation · Firmware

Validation firmware

A foundation for proving that a board works. Ready-made tests cover the hardware blocks of the STM32F767ZI and its board, from clocks and timers to serial buses, Ethernet and memory, and the framework is built for you to add tests for your own hardware.

C · FreeRTOS · LwIP

Features

  • Coverage for every hardware block: tests grouped by block, on the MCU and the board
  • Core, clocks and power: Cortex-M7 and FPU, faults, clocks and PLLs, power modes
  • Timers, DMA, RTC and watchdogs: plus interrupts, caches and the MPU
  • Serial and buses: UART, SPI, I2C, I2S, SAI, CAN and USB
  • Ethernet: ping, TCP and UDP tests on LwIP
  • GPIO, ADC and DAC: digital pins, analog inputs and analog outputs
  • Memory: internal flash, RAM, QSPI, FMC, SD card, option bytes and OTP
  • Display, camera and debug: LTDC, DCMI, DMA2D and JPEG, plus debug and trace
  • Console, script or GUI: JSON and Markdown reports for every board
  • Traceable and reproducible: every test maps to a requirement, and the build runs in Docker

09Validation · GUI

Validation GUI

A cross-platform desktop application for macOS, Windows and Linux that runs the HWVAL tests, streams results live, and keeps a searchable history of runs and reports. A built-in simulator lets it run without a board.

Python · PySide6 · SQLite

Features

  • Flexible test runs: single, group or full runs, with repeat and run-until-fail
  • Test catalogue: read from the firmware, with search and filters
  • Live results and prompts: operator prompts for tests that need a human
  • Run history in SQLite: compare, filter and export to CSV or JSON
  • Reports: JSON, Markdown and PDF
  • Firmware update: through the A/B bootloader, with downgrade warnings
  • SWD flashing: flash and provision through OpenOCD with live output
  • Built-in simulator: plus a TCP simulator server for other tools
  • Headless command line: distinct pass, fail and communication exit codes for CI
  • Operator mode: a simplified interface with an optional PIN

10Factory · Firmware

Factory firmware

The first firmware on a blank board: a compact FreeRTOS application, built in Docker and installed by the factory station. It stores each unit's identity, calibration and diagnostic data in a protected region of flash.

C · FreeRTOS · UART

Features

  • First application on the board: installed into slot A after the bootloader, signed with your key
  • Self-identification: name, version, build date and chip ID
  • Three protected data blocks: system information, calibration and diagnostics
  • UART commands: info, read, staged write and diagnostics init
  • Header and checksum validation: performed before anything touches flash
  • Chip binding: data issued for one chip is rejected by any other
  • Read-back verification: every programmed block is read back and compared
  • Write guard: writes outside the three blocks are refused
  • FreeRTOS base: health supervision and watchdog, built in Docker
  • Host tests: the production command handler runs against simulated flash

11Factory · Station

Factory station

A foundation for your production station. One guided flow takes a blank board to a finished unit: it programs the board, writes the unit's data, runs a self-test and records the result. A full simulator exercises every step without hardware; hardware integration is under active development.

Python · PySide6 · OpenOCD

Features

  • Guided flow: from a blank board to a provisioned unit
  • Device detection: discovers ST-LINK probes and UART ports
  • Bootloader over SWD: programmed once the dual-bank option bytes are set
  • Signed factory firmware: installed through the bootloader with your key
  • Per-unit data: system information from a CSV database, with calibration and diagnostics over UART
  • Read-back checks: every write is read back and compared
  • Identity protection: an address check guards the device identity record
  • Validation page: self-test of chip, flash, clock and RAM, with a saved report
  • Parallel fixtures: up to eight on one PC, with a full simulator for every step
  • Role-based PIN login: SQLite-backed, with automated tests and linting

12Factory · Data GUI

Factory data GUI

A desktop application that converts per-unit calibration, diagnostic and system data from a spreadsheet into the exact memory image the firmware stores in flash. Every record is validated first, and the CSVs and generated files are versioned together in Git.

Python · PySide6

Features

  • CSV in, files out: system information, calibration and diagnostics for every unit
  • Device-ready output: converts the data into the exact format the firmware stores
  • Four pages: system information, calibration, diagnostics and inspect
  • Line-level validation: the exact CSV line of every problem
  • Sanity warnings: flags values that are legal but suspicious
  • Manifest: size and checksums for every generated file
  • Verify Folder: reports files that changed, are missing or were never generated
  • Optional chip binding: a file is accepted by one chip only
  • Batch tool: sequential ID, serial and MAC assignment for a production run
  • Built-in Git: CSVs and outputs versioned together, with pull, commit and push from the app
